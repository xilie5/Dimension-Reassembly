# Compound Box - 完整开发执行计划

本文档是《可执行升级计划》的进一步落地版本，按标准游戏开发阶段组织：

```text
Pre-production
  -> Prototype
  -> Vertical Slice
  -> Production
  -> Alpha
  -> Beta
  -> Release Candidate
  -> Portfolio Release
```

目标版本：`Compound Box 1.0 Portfolio Slice`

## 1. 最终交付目标

### 游戏内容

- 15 个可完整通关的关卡
- 5 个递进区域
- 移动、推挤、整体传送、拆分、重组、精确切割、旋转
- 逐格材质、多材质复合体和复合目标
- 可移动传送节点
- 完整存档、解锁和最佳成绩

### 工程交付

- Unity 2022.3 LTS 工程
- Windows 64 位 Player
- 20 个以上 EditMode 自动化测试
- 关卡标准解回放验证
- 关卡编辑和验证工具
- 无编译错误、无警告
- 60 FPS 目标性能

### 作品集交付

- 一分钟核心玩法视频
- 三张不同区域的截图
- 架构图和技术说明
- 10 分钟面试讲解脚本
- README、GDD、技术设计和竞品分析

## 2. 开发原则

### 2.1 每次迭代都保持可运行

每个 Sprint 结束时必须：

- Unity 可以编译
- 当前关卡可以进入 Play Mode
- 旧测试全部通过
- Windows 构建仍可生成

禁止长期停留在“所有系统都改到一半”的状态。

### 2.2 先工具，后批量内容

当关卡数量超过 9 关后，手工修改文本布局会迅速变成负担。因此：

- 先完成 Schema V2
- 再完成编辑器
- 最后批量制作第 7 到 15 关

### 2.3 功能冻结优先于美术打磨

Alpha 之前可以替换白盒颜色和布局模板，但不再增加核心动词。

Alpha 后只允许：

- 修复 Bug
- 调整数值和关卡
- 改进反馈
- 完成美术替换

### 2.4 每个机制必须闭环

一个新机制从设计到完成必须包含：

1. 数据表示
2. Command 执行
3. Undo/Redo
4. 状态验证
5. 视觉预览
6. 音效和动画
7. 教学关
8. 对照关
9. 组合关
10. 自动化测试

### 2.5 每个 Sprint 只推进一个主要风险

不允许同一个 Sprint 同时承担：

- 核心数据重构
- 新动作
- 15 关内容生产
- 大量美术替换

| 玩法程序 | 数据模型、Command、模拟、存档 |
| 工具程序 | 编辑器、验证器、求解器、构建脚本 |

| 技术美术/美术 | 环境主题、物体轮廓、灯光和动画 |
| QA | 回归、边界、性能和发布检查 |

## 19. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 数据模型重构范围失控 | 高 | 高 | 保留 V1，分阶段迁移 |
| 15 关内容耗时超预期 | 高 | 高 | 先完成编辑器和求解器 |
| 高级机制组合过于复杂 | 中 | 高 | 每 Sprint 只加一个动作 |
| 传送和切割难度过高 | 中 | 中 | 增加 Ghost 预览和撤销 |
| 程序化白盒显得不完整 | 中 | 中 | 以统一视觉语法和灯光提升完成度 |
| 性能因预览和特效下降 | 中 | 中 | 对象池和性能门禁 |
| 范围膨胀 | 高 | 高 | 明确不做递归、重力和战斗 |
| 存档升级失败 | 低 | 高 | schemaVersion 和迁移测试 |

2. 建立 Sprint 任务表。
3. 定义 `EntityCellState` 和 `EntityConnection`。
4. 改造 `GridEntity` 并保留 V1 兼容层。
